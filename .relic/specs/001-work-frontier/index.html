Ranni 2

The work frontier agents leave behind

Ranni keeps the living state of in-flight work, meaning what is changing, why, where it stopped, and what was learned, as ordinary Relic records. Any agent, harness, or human can pick it up. Ranni never runs agents. Execution belongs to whatever harness the developer uses today, and that harness keeps evolving without Ranni's permission.

Product center: Relic indexes what the system should be; Ranni indexes the frontier of the work changing it. The goal is to take agent management off the developer's mind without freezing callers into a fixed runtime, protocol, or lifecycle.

Why Ranni 0.1 died

Ranni 0.1 was an MCP orchestrator. It failed for the same reason Relic 1.x did, which was rigidity in a world where agents change every month.

  • It owned execution: it spawned a fixed worker command, so every new harness capability (subagents, background sessions, worktrees, workflows, cloud) stayed outside it.
  • It demanded a self-contained task upfront, so the first human mistake propagated through the whole chain.
  • Workers had to end their output with a custom result block that the orchestrator parsed.
  • It kept a stored status machine (pending, running, awaiting_review, done_with_conflict…) that drifted from reality.
  • The machine made judgment calls: it auto-dispatched correction and conflict workers, and the skill required a polling loop.
  • The queue was gitignored runtime state, so what agents learned was lost.

Relationship with Relic

Ranni requires Relic. The dependency points one way: Ranni consumes Relic, and Relic never knows Ranni exists. Projects that use only Relic see no change.

  • Work items are an ordinary record kind declared by the host project in its relic.yaml, for example work: .relic/records/work with identities such as WORK-001. Relic reserves nothing for Ranni and Ranni adds no configuration file.
  • Ranni reads the kind named work by default; an option names another declared kind.
  • Selection goes through Relic's structured search (relic search --kind work --meta … --json), which Relic accepts on its own merits in its 003-structured-search specification. Ranni declares which versions of that JSON format it supports. Relic filters combine only with AND; when Ranni needs another combination, it runs several searches and merges the results itself.
  • Relic's search, viewer, verify, links, backlinks, and federation work on work items unchanged. In a federated project, work spread across member repositories composes for free.
  • There is no plugin contract in Relic. Ranni extends Relic by consuming its public read model, not by being loaded into it.

A work item is a living document

A work item is Markdown with only id required. The Ranni skill writes it with conventional sections, but neither Relic nor Ranni enforces them:

PartOwnerContent
Intent Developer; agents propose changes The outcome wanted and why. It may start rough; it is refined as knowledge appears.
Current frontier Whoever works on it Where it stopped, what was discovered, what changed in the plan, and the next step. It is rewritten, not appended; Git keeps the history.
Relationships Anyone Ordinary relative links to Relic specs and records it touches, and to work it depends on. Links become graph edges; frontmatter values stay opaque and are only filterable.

Refinement happens at the edge: the agent doing the work holds the freshest context, so splitting, rewriting, or narrowing a work item is the normal path, not a failure. Nothing has to be specified completely before work starts.

Relic leaves persistence to the developer. Ranni's governance for the work kind deliberately lets agents rewrite the current frontier without asking, because that is the burden being delegated. Changing intent, or closing, splitting, or removing a work item, still needs developer approval.

The only contract with executors

An executor references the work identity where it already leaves traces, and keeps the frontier current:

  • the branch name contains the identity, for example work/WORK-042-push;
  • commits carry a trailer such as Work: WORK-042;
  • the pull request title or body mentions the identity;
  • the current frontier section is updated at natural stopping points.

Any agent of any version, or a human, can satisfy this. There is no output block to parse and no tool the executor must call.

State is derived, never stored

Ranni keeps no status field and no queue. State comes from evidence at read time:

  • branches and commits referencing the identity, and how recently they moved;
  • pull requests referencing it: open, merged, closed, and unresolved review threads;
  • readiness: every linked dependency whose evidence shows merged work.

Evidence comes only from Git and the Git host, never from a specific agent harness, so the view keeps working when the harness changes. A project may keep a metadata field such as status for its own reasons; Ranni reads it as opaque input and never writes it.

Regression alarms

Stop and confront a proposal that brings back any of these:

  • spawning, scheduling, or configuring agents or workers;
  • a required output protocol, MCP tool, or callback that executors must speak;
  • a stored status, queue, lock, or lifecycle state machine;
  • automatic dispatch of follow-up work, or polling loops required by the skill;
  • a configuration file of Ranni's own, or a reserved topology inside Relic;
  • reading harness-specific session state as evidence;
  • parsing the Relic corpus itself instead of consuming Relic's read model;
  • compatibility layers whose purpose is to keep Ranni 0.1 behavior.

Open questions

  • Whether derived state ever needs to appear inside the Relic viewer. It is deferred until its absence actually hurts; Ranni shows its own view meanwhile.
  • The threshold for "stalled" and whether a project can tune it without a configuration file.
  • How the work frontier relates to CodeLeap Hub tasks: the Hub task owns the what and why for the client and team, and the work item owns the how and the frontier for agents.
